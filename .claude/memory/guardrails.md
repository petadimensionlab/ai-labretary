# Guardrails — 失敗から学んだルール

- **tokenize の前に生カウントであることを確認する**（2026-09-25）。`scripts/inspect_h5ad.py` の `counts_integer_like` が true、行和 ≈ `n_counts` であること。CELLxGENE の h5ad は `X` が正規化値で生カウントは `raw.X` にあることが多い。
  - 発端: PD_atlas サブセットの `X` が対数正規化値のまま tokenize されていた（logs/learnings-2026-09-25.jsonl）。
- **Geneformer V2 の ISP は `emb_mode: cls`（または `cls_and_gene`）必須**（2026-09-25）。V2 の tokenize は先頭に `<cls>` を付けるため `cell` だと `perturb_data` が停止する。状態重心（EmbExtractor）も同じ埋め込み種別で作ること（run_isp.py で連動済み・validate で検出）。
  - 発端: EXP-20260925-001 smoke が `Emb mode 'cls' or 'cls_and_gene' required` で失敗。テンプレートの既定値が `cell` だった。
- **bf16 で ISP するときはコサイン比較を fp32 で行う**（2026-09-26）。forward を bf16 にするだけだと `quant_cos_sims` が bf16 のまま計算され、shift（≈1 のコサイン 2 つの差, ~1e-4）が 2^-11 刻みに量子化される。run_isp.py の `apply_dtype` で fp32 に上げている。bf16 を新しい系で使うときは、同条件の fp32 と shift の順位を比較してから採用する。
  - 発端: EXP-20260925-001 smoke で素の bf16 は fp32 と Spearman ρ=0.43（n=8）、符号一致 4/8。
- **MPS でモデルを使った後のプロセスでは `datasets` の `num_proc>1` を使わない**（2026-09-26）。InSilicoPerturber 内の `map(num_proc=nproc)` が fork した子プロセスが `One of the subprocesses has abruptly died` で落ちる。MPS 実行の config は `perturbation.nproc: 1`（遺伝子ごと 100 細胞程度の map は 1 プロセスで数秒）。tokenize だけを別プロセスで行う場合は nproc を上げてよい。
  - 発端: EXP-20260926-001 phase 0 の bf16 精度ペア（compute.cache_model: true, nproc: 8）が 1 遺伝子目で停止。
- **効果の「比」で判定するときは、分子・分母の符号（正か負か）を必ず先に確かめる**（2026-09-26）。shift(A)/shift(B) は両方が負（goal から離れる）でも 1 を超える（例: LTBR −3.25e-4 / −1.65e-4 = 1.96, CI [1.02, 4.27]）。これは「A のほうが goal から大きく離れる」であり、「A で goal へ大きく近づく」という仮説の支持ではない。`validate_isp.py` の context_dependence は shift_A > 0 かつ shift_B > 0 を必須にし、shift_ratio に sign_A / sign_B を出す。比・倍率・fold change を報告するときは符号を併記する。
  - 発端: EXP-20260926-001 の validator が符号を見ずに LTBR の文脈依存性を True と判定（Labretary が検出、validator で修正）。
- **削除ドリフト（全遺伝子が全重心から一様に離れる）がある系では、「null の上位」は「goal へ近づく」を意味しない**（2026-09-26）。null が 100% 負のとき、上位 = ドリフトが小さいだけ（例: LCN2 は shift ≈ −1e-5 でほぼ無作用なのに null 分位 1.0）。反証条件の「文献が報告する向きが逆」も null 自体が負なら情報を持たない。null の符号分布（`null_frac_negative`）と HK 遺伝子の位置を必ず確認し、HK が陽性対照と同じく null 上位に入るなら陽性対照の「合格」は特異性を示さない。
  - 発端: EXP-20260926-001 で GAPDH/PPIA（HK）が shift_goal でも差分指標でも null 上位 10% に入った。
- **他の実験の `*.dataset`（tokenized など）を config で直接指さない**（2026-09-26）。HF datasets は `select`/`map` のキャッシュ（`cache-*.arrow`）を dataset ディレクトリ自体に書くため、読むだけのつもりでも元の実験ディレクトリが変更される。再利用するときはデータ部分（`data-*.arrow`, `dataset_info.json`, `state.json`）だけを `cp -c`（APFS clone）で自分の `work/` に複製し、sha256 の一致を記録する。
  - 発端: EXP-20260926-002 で EXP-001 の tokenized を再利用しようとした際、EXP-001 の tokenized.dataset に既に 190 個近い cache ファイルがあるのを確認（未遂で回避）。
- **fine-tuning の「checkpoint から再開」は、実際に途中停止 → 再開を一度通してから本番に使う**（2026-09-26）。torch ≥ 2.6（この環境は 2.14）+ transformers 4.46.3 では、`trainer.train(resume_from_checkpoint=...)` が `rng_state.pth`（numpy の乱数状態）を `torch.load(weights_only=True)` で読めず UnpicklingError で止まる。../Geneformer のパッチ済み Classifier の自動再開も同じ経路なので、中断すると再開できない。`finetune_classifier.py` は自分の checkpoint に限り numpy の型だけを `torch.serialization.add_safe_globals` で許可して回避（`weights_only=False` にはしない）。
  - 発端: EXP-20260926-003 の CPU smoke（小さなランダム BERT で 4 step → 再開）で検出。GPU を使う前に見つかった。
- **Claude Code の Bash サンドボックスは外部ネットワーク（tailnet の SSH/rsync を含む）を遮断する**（2026-09-26）。リモート接続が timeout したら、まずサンドボックスの影響を疑う（PI が承認した接続先に限り sandbox を外す）。`~/.ssh` もサンドボックス内からは見えない。
- **macOS の openrsync（protocol 29）は `rsync -a` で何も転送せずに成功終了することがある**（2026-09-26）。転送後は必ずリモートで `ls`/sha256 を確認する。`-av` で転送されたことを確かめる。
- **リモートの既存ファイルを rsync / scp で更新しても反映されないことがある**（2026-09-26, spark-cf5b。exit 0 なのに mtime・sha256 が古いまま）。コード・config など小さいファイルは `ssh HOST "cat > f.tmp && mv f.tmp f" < f` で書き、送った後に必ず sha256 を照合する（`scripts/remote/isp_remote.sh push` で実装）。
  - 発端: EXP-20260926-003 phase 3 で修正版 run_isp.py が届かず、古いコードで再実行して同じエラーになった。
- **datasets 4.8 系は `num_proc=1` でも fork したプールで map を実行する** → CUDA 初期化後は "Cannot re-initialize CUDA in forked subprocess"。run_isp.py の `single_process_datasets` で nproc ≤ 1 を None に変換（2026-09-26）。
- **サブエージェントが API の利用上限で途中停止すると、再開（SendMessage）できないことがある**（2026-09-26）。長い作業を任せるときは、途中経過（計画・判定・結果の README、learnings）をこまめにファイルへ書かせ、止まっても新しいエージェントがファイルから続けられるようにする。リモートのジョブ（tmux）はエージェントが止まっても続くので、再開前に `isp_remote.sh status` で状態を確認する。
- **bf16 forward で取った分類ヘッドの logits（`capture.classifier_logits`）は bf16 格子に量子化されている。ΔP / Δlogit を指標にするなら、飽和と量子化を先に確かめる**（2026-09-26）。`apply_dtype` がコサインを fp32 に上げても logits は bf16 のまま（|logit| 4〜8 で 2^-5 = 0.031 刻み）。FT 分類器が start 細胞で飽和（P(goal) 中央値 0）していると、|ΔP| の 99 パーセンタイルが 6e-5、Δ(logit 差) が厳密に 0 の細胞が 53% になり、遺伝子平均 ΔP は 0.3% の細胞に支配される（seed 間一致 0.27、細胞単位の長さ相関 −0.82 という見かけの構造が出る）。logits 系の指標を主指標にする計画では、分類ヘッドを fp32 で計算する（または fp32 の matched pair で確認する）ことと、P(goal) の分布（飽和）を事前に確認する。
  - 発端: EXP-20260926-005 run D の ΔP(PT_healthy)（事前登録の副指標）がほぼ 0 に潰れていた。
- **発現遺伝子の検出で goal ラベルを作ったら、埋め込みより先に「深さだけで何 AUC 出るか」を測る**（2026-09-27）。特定遺伝子が 1 カウント以上ある細胞は、総カウントや検出遺伝子数が多いほうへ偏る。識別の事前チェックでは深さだけのベースライン AUC を出し、トークン長をマッチさせた集合で主判定する。
  - 発端: EXP-20260927-002 の計画時点で、CCL19/CCL21/CXCL13 陽性の線維芽細胞（検出遺伝子数 中央値 2,064）と陰性（1,547）が、深さだけで donor 分割 AUC 0.676 に分かれた（閾値 0.65 超）。
- **`run_isp.py --dry-run` の内蔵見積もりを G2 の判定に使わない**（2026-09-27、2026-09-27 訂正）。当初「explicit の対照遺伝子を数えない」と書いたが、正確には **`controls.negative_random_n` が未設定のときに数えない**（明示すれば数える）。いずれにせよ内蔵見積もりは実測モデルより小さく出ることがあるので（実例: 内蔵 2.33 時間に対し実測モデル 4.0 時間）、**小さいほうは採らず**、遺伝子数 × 細胞数 × seed とトークン数からの実測モデルで見積もる。
- **埋め込みの出力とメタ情報を「行の位置」で突き合わせない**（2026-09-27）。Geneformer の EmbExtractor はバッチ処理のために細胞を並べ替えるので、`cell_embs.csv` と入力 dataset の行順は一致しない。一意な細胞 ID を `emb_label` に含めて出力させ、ID で結合する。
  - 発端: EXP-20260927-002 で `precheck_ci.py` が位置で結合しようとして停止した（位置が一致したのは 2,311 細胞中 39 だけ）。
- **仮説の G1 は、実験に着手する前に PI へ諮る**（2026-09-27）。計算が自動で進めてよい範囲（GPU 24 時間未満）で、方針の承認を受けていても、仮説の採択とは別である。方針の承認だけで実行に入ると、判定を記録するときに「採択されていない仮説の実験」になり、順序が逆になる。委託の前に tracker の status を確かめる。
  - 発端: 方針の承認（並行で進める）を受けて 2 つの実験を回したが、どちらの仮説も proposed のままだった。
- **合成データで検出力を事前に確かめるときは、遺伝子間のばらつきを実データから推定して入れる**（2026-09-27）。細胞のサンプリング誤差だけを模した合成データは、ばらつきを実データより大幅に小さく見積もる（実例: 4.6 分の 1）。その結果、合成では 3.5 標準偏差に見えた効果が実データでは 1.1 標準偏差しかなく、検出できない設計のまま事前登録してしまう。検出力の検査には、対照遺伝子の実測のばらつきを使う。
  - 発端: 合成データで「効果があれば検出できる」と確かめたのに、本番で陽性対照が 1 つも合格しなかった。
- **偶然合格率を見積もるとき、seed 間の独立を仮定しない**（2026-09-27）。同じ遺伝子の seed 間の値は相関するので、独立を仮定すると偶然合格率を過小評価する（実例: 見積もり 0.012 に対し実測 0.100 で約 8 倍）。対照遺伝子に同じ判定基準を当てはめた実測値で確かめる。
- **欠測（比べる相手が足りずに計算できなかった遺伝子）を「不合格」と数えない**（2026-09-27）。評価コードは、値が出なかった遺伝子と、出たうえで基準を満たさなかった遺伝子を分けて数える。対照の合否を報告するときは、まず値が計算できたかを確認する。
  - 発端: 分布の重なる対照遺伝子が下限に届かず判定不能だった遺伝子を、評価コードが「不合格」と数え、報告でも「期待と逆」と誤って伝えた。
- **過剰発現型の対象にする遺伝子は、計画の段階で「出発点で入力に載る細胞数」を数える**（2026-09-27）。過剰発現型は「発現している細胞で順位を最上位へ移す」操作なので、検出率の低い遺伝子は対象として成立しない（実例: 単一核データの CDKN1A は出発点の 0.75%・43 細胞で、seed を変えても同じ細胞になる）。発現頻度ではなく、実際に入力に載る細胞数を数えて、足りなければ主判定から外すか設計を変える。
- **目標ラベルを定義する遺伝子は、過剰発現型の健全性チェックに使えない**（2026-09-27）。出発点はその遺伝子が 0 の細胞と定義されるので、対象細胞が 0 になる。代わりに、別の軸の重心（例: 近縁の別の細胞状態）に対する既知マーカーの効果をパイプラインの陽性対照にする。
- **状態の重心は、深さ（読み取りの深さ）をそろえた後の細胞から作る**（2026-09-27）。重心の側で深さがそろっていれば、深さの交絡を元から断てる。
- **事前登録を固定した後に plan.md を触ったら、その場で変更ログを書き、sha256 を固定し直す**（2026-09-27）。承認や盲検解除の記録も「plan.md の変更」であり、固定のハッシュは中身を区別しない。追記だけして再固定を忘れると、実行担当の照合が落ちて計算が止まる（あるいは、気づかれずに実行されると「承認を記録する文書が無記録で変わった」状態になる）。plan.md に書き足すときは、(1) 変更ログ（日時・理由・結果を見る前か後か）、(2) 承認チェックリストの更新、(3) ハッシュの固定し直し、の 3 つを必ずまとめて行う。
  - 発端: 固定後に盲検解除を plan.md へ追記したが、チェックリストの更新と再固定を忘れ、実行前チェックで不一致になって実験が止まった。
- **バージョン管理下にないプロジェクトでは、「変更したのはここだけ」は申告であって証明ではない**（2026-09-27）。差分を機械的に照合できないので、固定後の変更は「何を変えたか」を本人がその場で書き残すしかない。書き残していない変更は復元できない。
- **learnings に 1 行追記したら、その場で JSON として読めることを確かめる**（2026-09-27）。シェルの echo でクォートを書き間違えると壊れた行が混ざり、あとから機械的に読めなくなる。追記は python の `json.dumps` で行い、書いた直後に全行を読み直して検証する。
  - 発端: `,"action"` を `" "action"` と書き間違えて壊れた行を追記し、読み込み時に例外になった。
- **過剰発現型で「1 つの重心への接近度」を主指標にしない**（2026-09-27）。過剰発現には、どの重心へも一様に近づく成分がある（実測: 対照遺伝子で、目標への接近度と無関係な別状態への接近度の相関 ρ = 0.91〜0.95）。この指標は方向ではなく移動量の大きさを測ってしまう。目標に特異的な成分（目標への接近 − 別の状態への接近）を主指標にするか、計画の段階で重心どうしの相関を測って、単一重心の指標が使えるかを確かめる。
  - 発端: 恒常発現遺伝子 GAPDH が対照の最上位に来た。原因は目標へ近づいたことではなく、移動量が全遺伝子中で最大級だったこと（目標に特異的な成分では下位 0.04〜0.15）。
- **陽性対照は、主判定で使う軸と同じ軸で用意する**（2026-09-27）。別の軸で動くことを示しても、目標の軸で動かせることの証拠にはならない。「系は動いている」と言えるのは、主判定の軸で何かを動かせたときだけ。
  - 発端: 筋線維芽細胞の軸では陽性対照が強く動いた（q=1.0）が、目標の軸で摂動が効くことは一度も示されないまま「系は正常」と読みかけた。
- **指標を「方向に特異的な形」に替えたら、順位だけの判定規則を使い回さない**（2026-09-27）。方向に特異的な指標は、対照遺伝子のばらつきのうち遺伝子ごとに再現する成分が大きくなる（実測: 32% → 82%）。すると **seed を重ねても偶然合格率が下がらない**（同じ遺伝子が毎回同じ側に出るため）。順位の条件に加えて、**絶対的な大きさの条件**（対照の標準偏差の何倍か）を併せて課し、候補の個数ぶんの偶然合格率を対照遺伝子で実測してから事前登録する。
  - 発端: 前の実験の規則をそのまま新しい指標に当てはめたら、候補 10 個で 1 つ以上が偶然合格する確率が 0.67 になり、陽性対照の検査にならないと分かった。
- **過剰発現型の対象にできるかは、発現細胞数だけでは決まらない**（2026-09-27）。計画の段階で次の 2 つを数える。(1) **提供者あたりの上限を当てた後**に実際に取れる細胞数（発現細胞が足りても、提供者が偏っていると下限に届かない）、(2) その遺伝子と**比べられる対照遺伝子の数**（元の位置の広がりが大きい遺伝子は、そろえられる相手が足りず構造的に判定不能になる）。
  - 発端: 偏りが最大の候補が提供者上限で細胞数に届かず、別の候補は比べられる対照が 11〜15 個しかなく、どちらも計画段階で落とした。
- **事前登録を sha256 で固定する前に、`run_isp.py --dry-run` を通す**（2026-09-27）。固定してから実行時に設定の不備が出ると、そのたびに「事前登録ファイルの修正 → 変更ログ → チェックリスト → 再固定」が必要になり、**承認を記録する文書を何度も書き換えることになる**。dry-run は計算を一切しないので、固定の直前に必ず通す。計画のチェックリストに「dry-run が通ることを確認した」の項目を入れる。
  - 発端: 固定後の実行時に、必須セクションの欠落と、実行スクリプトが対応していない設定の書き方（外部ファイル参照）が続けて見つかり、実験が 2 回止まった。
- **設定ファイルには、実行スクリプトが実際に読める書き方しか使わない**（2026-09-27）。遺伝子リストを別ファイルに置いて設定から参照する、といった書き方を新しく考えたときは、**実行スクリプト側がその書き方に対応しているかを先に確かめる**。対応していないなら、(1) 設定に直接書く、(2) 実行スクリプトに対応を足す（共有スクリプトの変更なので他の実験への影響を確認する）、のどちらかを選ぶ。

- **「遺伝子をまとめれば効果が増える」と考える前に、変位ベクトルどうしの方向が揃っているかを測る**（2026-10-03）。同時摂動で余弦が増える理屈は「目標の軸に沿った成分は n 倍、無関係な成分は √n 倍」だが、**これは変位どうしが直交している場合の話**である。実測では変位どうしの平均コサインが 0.24〜0.47 あり、**増幅率は √n（119 個で 10.9）ではなく 0.97〜1.95 にとどまった**。→ 既存の埋め込みから「個々の余弦の平均」と「和の余弦」を計算し、その比を見る（`experiments/EXP-20261001-001/posthoc-combo/coherence.py`）。**摂動を回さずに計算できる。**

- **「既知の生物学を再現した」と言う前に、一致率のベースラインを測る**（2026-10-03）。スクリーンの上位 27 遺伝子を文献照合して 13/18（72%）で文献が報告する向きと一致したが、**上位だけを調べているので較正されていない**。無作為に選んだ遺伝子でも、線維化・腎臓は研究が多いので一定の割合で「関連あり」の報告が見つかる。→ **対照から無作為標本を抜いて同じ照合を行い、一致率を比べる。** 比べていない一致率は、発見の根拠にならない。
- **文献との一致を「再現」と言えるのは、偏りのない部分で一致したときだけ**（2026-10-03、較正で判明）。スクリーンの上位を文献照合して 72% が一致したが、**無作為な対照のベースラインも 71% で差が無かった**。さらに**生物学的な理由で選んでいない対照プール由来の上位 9 個だけを見ると、文献が報告する向きが一致 0 件・文献が報告する向きが逆 2 件**だった。一致したのは**そもそも文献を根拠に選んだ遺伝子**ばかりで、循環である。→ **上位ヒットを「選んだ遺伝子」と「選んでいない遺伝子」に分け、後者だけで一致率を見る。** 前者の一致は証拠にならない。
- **スクリーニングの外れ値を 1 個取り出して論じる前に、その水準に達する遺伝子が偶然いくつ出るかを計算する**（2026-10-03、Labretary が ENG で誤った）。ENG の z = −3.67 を「文献との正面衝突」として報告したが、**対照 1,000 個で z ≤ −3.66 は 1 個しかなく、217 遺伝子では期待 0.22 件・P(1 件以上) = 0.20**。偶然の範囲だった。→ **期待件数 =（対照での経験的な片側割合）×（検定した遺伝子数）** を先に出す。
- **対照の z 分布が正規とは限らない。正の側と負の側を同じ基準で読まない**（2026-10-03）。実測の歪度 +1.70・尖度 12.19 で**負の裾が薄い**。正の側は z ≥ +4.0 が期待 1.3 件に対し 7 件で偶然を超えるが、**負の側は校正されていない**（対照 1,000 個中 1 個）。→ **抑制する方向の候補を出すときは、負の側に目盛りが立っているかを先に確かめる。** 立っていなければ「抑制側の候補」と書かない。
- **目標の軸が狭すぎないかを、重心どうしの角度で確かめる**（2026-10-03）。本研究の目標と出発点の重心は**コサイン 0.999、角度にして 2.5 度**しか離れていない。変位のうち目標の軸に沿う割合は最大 17%・中央値 −0.5% で、z はこの小さなコサインを拡大した値である。→ **着手前チェックに「重心どうしの角度」を記録する。** 角度が小さいほど、同じ摂動でも読み取れる信号が小さくなる。
- **「計算量が小さいから手元の Mac で回す」は、既存の分布で標準化する実験では成り立たない**（2026-10-03、Labretary が依頼文に「Mac で回すほうが簡単」と書いた誤りを、機体の一致確認が止めた）。Mac（MPS）と CUDA では**埋め込みの最大差 0.15625、主指標の中央値の差 0.0155**。この 0.0155 は**対照 12 個の主指標の中央値のばらつき（標準偏差 0.0148）と同じ大きさ**で、新しい遺伝子だけに対照 1 個分の系統的なずれが乗る。→ **既存の対照で標準化する実験は、既存と同じ機体で回す。** 小規模でも例外にしない。記憶の「Geneformer は MPS でも動作する」は**動くこと**の話で、**同じ値が出ること**ではない。

- **事前登録の解釈の規則は、「両方が当たる」場合も先に書く**（2026-10-03）。ACTA2 と MYH11 を排他的に扱う規則（ACTA2 が超える／ACTA2 が超えず MYH11 が超える／どちらも超えない）を書いたが、**実際は両方が超えた**。規則が想定していない形だったため、解釈を事後に足すことになった。→ **2 つの候補を対比させる規則では、「両方」「どちらでもない」の 4 通りすべてに、結果を見る前の読み方を書く。**
- **「〜だから合わない」と原因を書く前に、条件を 1 つずつ振って切り分ける**（2026-10-04、PI の指摘「比較検証するのみ、条件違うか確かめず、違って停まったりしてて、おまえら適当に仕事してるやろ？」）。Mac の機体照合が落ちたとき、Labretary は「MPS と CUDA の数値の違い」と断定して止めたが、**切り分けを一度もしていなかった**。実際に振ってみると（`transformers` 4.46.3 / `torch` 2.14.0、同一の重み sha256 `965ceccea8…`）、**同じ Mac の CPU だけで注意機構の実装を eager → sdpa に変えると最大差 0.3125** で、観測された Mac の不一致 0.15625 より**大きい**。→ **不一致を見たら、(a) 重み、(b) 計算バックエンド、(c) ライブラリの版、(d) 数値型 を 1 つずつ振って、どれが効いたかを数値で言えるまで原因を書かない。** 突き合わせただけで止めるのは比較であって診断ではない。
- **機体間で再現しない原因は bf16 であって、装置ではない**（2026-10-04、実測）。同じ重み・同じ入力で 4 条件（CPU/MPS × eager/sdpa）を回すと、**bf16 では 0.219〜0.375（相対 1.2〜2.1%）ずれるのに対し、fp32 では 1.8e-5〜2.4e-5（相対 0.0001%）** まで一致する。**MPS と CPU の差も fp32 では 1.8e-5 しかない。** 18 層を bf16（仮数 8 bit）で通すと、積和の順序がわずかに変わるだけで相対 1% 級の差が出る。→ **機体照合の許容差 1e-6 は bf16 では原理的に達成できない。** 達成できていたのは cf5b と c083 が同一の CUDA カーネルを使っていたからで、「同じ機体なら合う」ではなく「**同じカーネルなら合う**」である。**別の機体を使いたいなら dtype を fp32 にする**（`scripts/remote/retired/` ではなく config の `dtype`）。「Mac は使えない」は装置の制約ではなく、**自分たちの dtype の選択の帰結**である（「制約と書く前に実装を読む」2026-10-03 と同型の誤り）。
- **マーカーの定義は 1 通りではない。「全員合格／全滅」の規則を主判定にしない**（2026-10-04、PI の指摘「全部揃わなあかんとは限らんやろ？人によってマーカーの定義も違うんやで。柔軟性もない」）。EXP-20261003-001 の解釈の規則は「6 個とも満たさない → 軸は測っていない」という全滅条項を置いていた（実際は規則 1 が当たり発動していない）。筋線維芽細胞のマーカーは研究者によって ACTA2 単独・ACTA2+TAGLN・収縮性 3 個など採り方が違い、**どれが「正しい」組かは決まらない**。→ **マーカーの組で判定するときは、(a) 組を複数とって結論が変わらないかを示し、(b) 閾値を使わない読み方（対照からの並べ替え検定）を併記する。** 実測では ACTA2 単独 p=0.005、ACTA2+TAGLN p=0.004、収縮性 3 個 p=0.007、+MYH11 の 4 個 p=0.0007、6 個すべて p=0.0003 と**どの定義でも結論は同じ**だった（`experiments/EXP-20261003-001/work/graded_read_008.json`）。
- **「記録なし」どうしを一致と見なす検査を書かない**（2026-10-04、作った直後に自分で踏んだ）。`compare_conditions.py` の初版は、両方の結果に注意機構の実装も `transformers` の版も記録が無いとき、**「すべて一致」と表示して終了コード 0 を返した**。突き合わせられていないのであって、同じだと確かめたわけではない。**この検査が防ごうとしていた失敗そのものを、この検査が見逃した。** → **欠測は不一致として扱う。** 比較の検査を書いたら、**値が無い入力を 1 回通して、落ちることを確かめる。**
